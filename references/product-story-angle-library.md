# 产品故事与推广角度库

这个参考文件重点解决三个问题：产品亮点怎么展示、开发过程怎么讲、用户案例怎么呈现。

## 一、产品亮点展示

### 亮点选择原则

优先选择：

- 最容易被目标用户理解的功能。
- 使用前后变化最明显的结果。
- 最适合截图或录屏的过程。
- 最能体现产品特点的动作。
- 用户最常遇到的场景。
- 最能产生漂亮、清晰或有用成果的功能。

### 亮点展示结构

```text
人物和场景
原来的麻烦
产品中的关键动作
结果画面
结果中的一个细节
这个亮点适合谁
```

### 六种亮点画面

#### 1. 输入到输出

同时展示：原材料、产品操作、最终结果。

适合生成、整理、分析、设计、编辑和自动化产品。

#### 2. 使用前后

左边或前几页展示旧状态，右边或后几页展示产品处理后的状态。

#### 3. 一个步骤消失了

把原流程中最麻烦的一步单独拿出来，展示产品怎样把它缩短或整合。

#### 4. 一个结果的细节

不展示全部产品，只放大结果中最能体现价值的一处。

#### 5. 三个场景共用一个功能

同一个功能分别用于三个相近但不同的任务，让用户迅速理解适用范围。

#### 6. 完整任务

从一个明确任务开始，连续展示产品如何完成直到结果出现。

### 亮点内容卡

```text
亮点名称：
目标人物：
使用时刻：
原来的状态：
产品动作：
最终结果：
需要展示的细节：
图文结构：
短视频结构：
所需素材：
```

## 二、开发过程展示

### 1. 开发起因

结构：

```text
反复遇到的问题
最后一次触发
第一个简单解决办法
为什么继续把它做成产品
第一版长什么样
```

可用素材：原始笔记、草图、第一版截图、手工流程、第一次录屏。

### 2. 第一版与现在

结构：

```text
第一版想解决什么
第一版最明显的问题
中间改过的关键部分
当前版本出现了什么变化
```

适合做前后对比图文或版本演进视频。

### 3. Bug 与修复

结构：

```text
画面中出现什么错误
这个错误会影响什么
开发者最初以为原因是什么
最后发现了什么
修复前后有什么变化
```

Bug 内容要让普通用户也能理解，避免只展示代码和报错。

### 4. 产品取舍

结构：

```text
两个都想要的目标
为什么不能同时做到
最终选择了哪一个
这个决定怎样影响产品体验
```

常见主题：速度与细致、自动与可控、简单与专业、功能多与上手快。

### 5. 删除功能

讲清：为什么做、为什么删、删掉后产品反而哪里更清楚。

### 6. AI 参与开发

讲清：AI 做了什么、哪里做错了、开发者怎样判断和修正、最后产品发生什么变化。

不要只做快速闪过的代码画面，要让用户看到一个具体产品变化。

### 7. 一条反馈改变产品

结构：

```text
原来的设计
用户使用时卡在哪里
开发者怎样理解这句话
具体改了什么
新版本的画面
```

### 8. 发布这一版的决定

讲清这版保留了什么、暂时没有做什么，以及开发者希望用户重点体验哪部分。

### 开发故事卡

```text
事件：
冲突：
关键画面：
产品决定：
用户能看到的变化：
图文表现：
视频表现：
需要的旧素材和新素材：
```

## 三、用户案例展示

根据现有材料选择表达形式。

### 1. 完整用户案例

```text
用户是谁
当时在做什么
原来怎样处理
遇到什么麻烦
怎样使用产品
使用过程中做了哪些动作
最后得到什么结果
结果后来怎样被使用
```

### 2. 匿名用户故事

保留职业、场景、流程和结果，去掉不需要公开的身份信息。画面以产品操作和结果为主。

### 3. 创始人实测

创始人用自己的真实任务完成一次完整演示：准备输入、开始操作、处理中遇到的问题、最终结果、结果中最值得看的细节。

### 4. 样例使用场景

使用公开材料或准备好的样例输入，展示一个典型任务怎样完成。内容重点放在过程和结果，不假装出现了具体客户。

### 5. 用户的一句话展开

从一句反馈中提取：背景、问题、产品动作和结果，再配产品画面和完整说明。

### ToC 案例重点

- 一个人的具体时刻。
- 使用前后的体验变化。
- 产品结果和个人感受。
- 是否愿意继续使用或展示结果。

### ToB 案例重点

- 公司或团队背景。
- 使用者岗位。
- 原来的工作流程。
- 产品进入流程的位置。
- 团队收到的结果或交付物。
- 使用过程中涉及的协作变化。

### 案例内容卡

```text
案例形式：
人物或团队：
使用场景：
原状态：
产品动作：
结果画面：
关键细节：
图文页序：
视频分镜：
所需素材：
```

## 四、创始人故事

创始人内容从具体事件开始：

- 为什么只解决这个小问题。
- 哪次使用让自己觉得产品值得继续做。
- 最难放弃的功能是什么。
- 一个用户行为怎样推翻原来的想法。
- Vibe Coding 帮助做出了什么，仍有哪些判断必须由人完成。
- 这个产品最希望给用户留下什么感受。

每个创始人故事都要出现产品、用户或开发决定，避免变成空泛创业感悟。

## 五、内容角度库

### 问题类

1. 用户一天中最容易被打断的步骤。
2. 看起来很小、累计起来很麻烦的动作。
3. 一张图展示旧流程有多少环节。
4. 用户通常怎样凑合解决。

### 结果类

5. 一张输入怎样变成最终结果。
6. 使用前和使用后的画面。
7. 最快能看到的第一个结果。
8. 最值得放大的结果细节。

### 开发类

9. 第一版长什么样。
10. 一个 Bug 怎样改变产品。
11. 为什么删掉一个功能。
12. AI 做错的一件事。
13. 最难做的产品取舍。
14. 一条反馈带来的修改。

### 案例类

15. 创始人亲自完成一次任务。
16. 一个匿名用户的完整过程。
17. 同一个产品在三个场景中的用法。

### 教程类

18. 从零完成一个任务。
19. 三个容易出错的地方。
20. 一份可以直接照着做的清单。
21. 初级用法和进阶用法。

### 对比类

22. 手工处理和产品处理。
23. 复杂方案和简单方案。
24. 适合用产品与暂时不适合的情况。

### 观点类

25. 为什么这个小问题值得做成产品。
26. 做完产品才发现的用户习惯。
27. 开发前后完全不同的一个判断。

根据具体产品改写以上角度，不直接把这些通用标题交给用户。
